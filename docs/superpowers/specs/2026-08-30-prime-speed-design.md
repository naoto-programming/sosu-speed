# 素数スピード — 設計書

## 概要

2人対戦のブラウザカードゲーム。場に置かれた合成数を素因数分解し、対応する素数カードを出していく。自分の山札の最後（Stopカード）を引いた方が勝ち。

技術スタックはプレーンな HTML / CSS / JS（ビルド不要、フレームワーク不使用）。既存の空ファイル `index.html` / `style.css` / `game.js` を実装する。ビジュアルは `nabla-game-master` の配色・フォント・ボタンスタイルを踏襲するが、カード描画は Canvas ではなく HTML/CSS の角丸カード要素で行う。

## 定数

```js
const PRIMES = [2, 3, 5, 7, 11];
const DEFAULT_MAX_COMPOSITE = 1100;
const DEFAULT_COUNT_PER_PRIME = { 2: 6, 3: 6, 5: 6, 7: 6, 11: 6 };
const HAND_SIZE = 5;
```

## 配色・スタイル（nabla-game-master 準拠）

- `--color-dark: #232248`（濃紺）／ `--color-light: #fffcf9`（クリーム）
- 見出しフォント: `'Roboto Slab'`（Google Fonts）
- ボタン: クリーム背景・濃紺3px枠・角丸5px・太字。`:active` で色反転
- カード: クリーム背景・濃紺2〜3px枠・角丸8〜10px・中央に大きな数字。box-shadowで軽い浮き上がり

## 画面構成

1. **タイトル画面** (`#screen-title`): タイトル、「対戦開始」ボタン、「設定」ボタン
2. **設定画面** (`#screen-settings`): 素数ごとの山札枚数（2,3,5,7,11 それぞれ数値入力）、合成数の最大値（数値入力、デフォルト1100）、「デフォルトに戻す」「対戦開始」ボタン
3. **ゲーム画面** (`#screen-game`): 詳細は下記
4. **ゲーム終了画面** (`#screen-gameover`): 勝者表示、「もう一度」ボタン

### ゲーム画面レイアウト

- 上部: プレイヤー2の手札（5枚、カード）＋ 山札残り枚数
- 中央: 現在の合成数（大きく表示）／ これまで出したカードの一覧（例: `5 × 3`、出すたびに伸びる）
- 下部: プレイヤー1の手札（5枚、カード）＋ 山札残り枚数
- 両プレイヤーの手札は常に表向き（同一画面を共有するローカル対戦のため、相手の手札を隠す機構は設けない）
- **出せる/出せないカードの視覚的ヒントは一切表示しない**（`.playable`/`.disabled`のような色分けなし）。プレイヤーは合成数を自力で素因数分解し、どのカードが出せるかを自分で判断する。素因数分解の結果（内訳チップ表示）も表示しない

## データモデル

```js
Player {
  hand: number[]        // 手札の値の配列（5枚）
  deck: (number|'STOP')[]  // 山札。末尾が必ず'STOP'
}

GameState {
  players: [Player, Player]
  composite: number          // 現在場にある合成数(表示用の元の値。カードを出しても変わらない)
  remaining: { [prime]: count }  // 残り必要な素因数の枚数(内部判定用。画面には出さない)
  previousComposite: number | null
  compositePool: number[]    // 起動時に列挙した「出現しうる合成数」の全リスト
  playedLog: number[]        // 現在の合成数に対してこれまで出した値の並び。合成数が切り替わるとリセット
  winner: 0 | 1 | null
}
```

## ロジック

### 山札生成

各プレイヤーごとに独立に：
1. 設定枚数分の素数カード配列を作る（例: 2が6枚, 3が6枚...）
2. Fisher-Yatesでシャッフル
3. 配列の末尾に `'STOP'` を1枚追加（シャッフル対象外、常に最後）
4. 先頭 `HAND_SIZE` 枚を手札として取り出す（`splice(0, 5)`）

### 合成数プールの列挙

起動時（または設定変更時）に一度だけ計算：

```js
function enumerateComposites(max, primes) {
  const pool = [];
  for (let n = 4; n <= max; n++) {
    if (isValidComposite(n, primes)) pool.push(n); // 許可された素数だけで分解でき、素因数の総数が2以上のものだけ採用
  }
  return pool;
}
```

これにより場に出る合成数は必ず現在のルールの素数カードだけで分解可能になる。ただし、これだけでは「山札の素数構成に対して合成数の最大値が小さすぎる」ケース（詳細は「エッジケース」参照）を防げないため、`minimumMaxCompositeFor` による事前チェックと組み合わせて使う。

`enumerateComposites` は `max` に比例した回数の試し割りを行うため、設定画面の合成数の最大値入力には `max="100000"` を設け、極端に大きい値による実行時間の肥大化を防いでいる。

### 次の合成数を選ぶ

合成数プールから単純にランダム選択すると、選ばれた合成数がどちらの手札でも出せない（＝即座に膠着する）場合がある。これを避けるため `pickPlayableComposite(compositePool, previous, hand0, hand1, randomFn)` は次の手順で選ぶ：

1. `compositePool` を「その合成数の素因数分解結果に対して、少なくとも一方の手札に出せるカードがある」もの（＝`bothStuck` が false になるもの）だけに絞り込む
2. 絞り込んだ結果が空なら（理論上は起こらないはずだが安全のため）元の `compositePool` 全体にフォールバックする
3. 絞り込み後のプールに対して `pickNextComposite` を呼び、`previousComposite` と異なる値を（候補が2つ以上あれば）ランダムに1つ選ぶ
4. 選んだ値の素因数分解結果（例: 60 → `{2:2, 3:1, 5:1}`）で `remaining` を初期化する

初期化時（`createGameState`）と、クリア・膠着判定で合成数を切り替えるとき（`applyPlay`）の両方でこの `pickPlayableComposite` を使うことで、場に出た瞬間から膠着している合成数が選ばれることはない。

### カードを出す（クリックハンドラ）

見た目のヒントが無いため、全てのカードに常にクリックハンドラを付ける（出せる/出せないは押してみるまで分からない）。

1. クリックされたカードの値 `v` について `remaining[v] > 0` かを確認
   - **0以下（間違ったカード）の場合**: ゲーム状態は変更せず、そのプレイヤーの手札全体を`MISPLAY_COOLDOWN_MS`(既定2000ms)の間ロックする（「お手つき」）。ロック中は手札の全カードからクリックハンドラを外し、`.locked`クラスで見た目上も分かるようにする。カード自体は手札から失われない。ロック中に再度クリックしてもロック時間は延長されない。ロックは時間経過で自動的に解除される（`setTimeout`で再描画）
   - **正しいカードの場合**: 以下の2〜5を実行
2. 手札から該当カードを1枚取り除き、`remaining[v]` を1減らし、出した値を`playedLog`の末尾に追加する
3. 自分の山札の先頭から1枚引いて手札に加える（5枚に戻す）
   - 引いた札が `'STOP'` の場合: 即座にそのプレイヤーの勝利として `winner` を確定し、ゲーム終了画面へ
4. `remaining` の全値が0になったか判定 → クリア済みなら次の合成数を選ぶ（`previousComposite` を今引いた値に更新し、`playedLog` を`[]`にリセットする）
5. クリアしていなければ「膠着判定」を行う（下記）

同時タップについて: JSはシングルスレッドでクリックイベントは1件ずつ順に処理されるため、2人が同時に近いタイミングでカードを叩いても、後から処理された方は常に更新済みの`remaining`を見て正しく判定される（構造上レースコンディションは起きない）。画面が崩れないようにするための追加の排他制御は不要で、上記の手札ロック機構だけで「お手つき連打」を防げば十分。

### 膠着判定（詰み）

出す/引くイベントの後、`remaining` に残りがある状態で、両プレイヤーの手札のどのカードも `remaining[v] > 0` を満たさない（＝どちらも出せる手がない）場合、現在の合成数を強制的に破棄し、次の合成数を選ぶ（`playedLog`もリセットされる）。

### 場の数字の表示モード（設定でオンオフ）

設定画面のチェックボックス「出したら合成数を割った値を表示」（既定OFF）で切り替える:

- **OFF（既定）**: 場には常に元の合成数（例: 810）を表示し続ける。プレイヤーは`playedLog`（例: `5 × 3`）を見ながら、残りをどう分解すべきか自力で追う必要がある
- **ON**: 場の数字を `computeQuotient(composite, playedLog)`（＝元の合成数を、出した値で順番に割った値。例: 810 → 5を出す → 162 → 3を出す → 54）に更新する。`playedLog`の表示自体は両モードで変わらない

### 勝利条件

いずれかのプレイヤーが自分の山札から `'STOP'` を引いた瞬間、そのプレイヤーの勝利で即終了。

## エッジケース

- **合成数の最大値が、山札の素数構成に対して小さすぎる場合**: `minimumMaxCompositeFor(countPerPrime, primes)` が「山札に含まれる素数のうち最大のものの2倍」（例: 11のカードが1枚でもあれば22）を必要最小値として返す。`startGame()` はこれと設定値を比較し、設定値が下回っていれば必要最小値まで自動的に引き上げてアラート表示する。入力には `min="4"` に加え `max="100000"` も設けている。
- **山札の総枚数が手札枚数(`HAND_SIZE`=5)未満の場合**: `buildDeck` はシャッフル後の実カード列の末尾に必ず `'STOP'` を1枚追加するが、`dealHand` は先頭 `HAND_SIZE` 枚を無条件に手札へ切り出すため、実カード枚数の合計が4枚以下だと配布直後の手札に `'STOP'` が混入し、山札が空になって以後誰も `'STOP'` を引けず永久に手詰まりになる（設定画面の各カード枚数入力は `min="0"` のためUIから到達可能）。これを防ぐため `startGame()` は `countPerPrime` を確定させた直後、`minimumMaxCompositeFor` のチェックより前に総枚数を計算し、`HAND_SIZE` 未満ならデッキ構成をデフォルト（`DEFAULT_COUNT_PER_PRIME`、各6枚）に戻してアラート表示する。
- 山札枚数設定を0にした素数がある場合（かつ総枚数は`HAND_SIZE`以上を維持している場合）: その素数は合成数の分解結果に出現しても手札・山札のどこにも存在しないため詰み判定が正しく機能する（膠着扱いになるだけで壊れない）

## ファイル構成

- `index.html`: 画面構造（4画面をすべて記述し、`hidden`属性で切り替え）。ゲーム画面には常時「タイトルに戻る」ボタン(`button-QUIT_TO_TITLE`)を配置する
- `style.css`: nabla-game-master準拠の配色・フォント・ボタン・カードスタイル
- `logic.js`: DOMに依存しない純粋なゲームロジック（素因数分解、合成数プールの列挙・選択、山札生成、手札配布、状態遷移である`createGameState`/`applyPlay`など）を独立ファイルとして分離。Node.jsの`node:test`から`require`して単体テストできるよう、`module.exports`でエクスポートする
- `game.js`: DOM描画・イベントハンドラ・設定の読み書きなど画面側のロジック。`logic.js`が公開する関数・定数を利用する。フレームワーク不使用のバニラJS
- `tests/logic.test.js`: `logic.js`の単体テスト（`node --test tests/logic.test.js`で実行）
